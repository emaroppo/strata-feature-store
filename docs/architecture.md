# Point-in-Time Feature Store — Architecture

**Status:** design, pre-implementation
**Scope:** offline feature storage and composition for revised panel data

---

## 1. What this is

A feature store for **panel data that gets revised** — official statistics, indicators,
derived event features — where the correct answer to "what was the value of X" depends
on *when you ask*.

The central capability is point-in-time correct composition: a feature query resolved
as-of April returns what was knowable in April, not what we know now. Naive joins on
event date leak future information into training sets and silently inflate backtest
performance.

**Explicitly out of scope:** online serving / low-latency feature retrieval. There is no
serving latency requirement, and an online store is most of the complexity in Feast or
Tecton. This is an offline store only.

**Deferred, not excluded:** blobs, records, labels, model registry, processing-step
registry, entity knowledge base. All are additive — see §11.

---

## 2. Division of responsibility

| Layer | Holds | Answers |
|---|---|---|
| **Postgres** | catalog: descriptions, pointers, lineage | *what exists, where did it come from* |
| **Parquet** | feature values, long format | *what are the values* |
| **Garage (S3)** | bytes | storage and retrieval |
| **Object key path** | hive partition values | partition pruning |

Postgres holds **zero feature values**. It stays in the low megabytes even after bulk
ingest of every World Bank / IMF / UN dataset.

Storage is accessed over the S3 API throughout (`boto3` for object operations, DuckDB
`httpfs` for parquet reads). Garage locally; the same code runs against S3, R2, or Ceph
by changing `endpoint_url`. There is deliberately **no `StorageBackend` abstraction** —
one code path, one configurable endpoint.

## 3. Catalog schema

```
entity_namespace(name PK, description, external_ref, created_at)

dataset(id PK, name UNIQUE, kind, entity_namespace FK NULL,
        license, source_url, description, created_at)

dataset_version(id PK, dataset_id FK, version_num, resolution_mode,
                spec JSONB, content_hash, frozen_at, created_by_run_id FK)

feature_group(id PK, name UNIQUE, dataset_id FK, entity_namespace FK,
              granularity, time_basis, storage_prefix,
              partition_spec JSONB, meta JSONB, created_at)

feature(id PK, feature_group_id FK, name, dtype, unit, description,
        created_by_run_id FK, deprecated_at NULL,
        UNIQUE(feature_group_id, name))

run(id PK, kind, name, config_hash, code_git_sha, code_dirty,
    params JSONB, env JSONB, status, started_at, finished_at)

run_input(run_id FK, ref_type, ref_id, role)
run_output(run_id FK, ref_type, ref_id, role)
```

Notes:

- `feature` is a **vocabulary registry** — one row per feature name in the group — not a
  description of physical columns. Full WDI is ~1,400 rows.
- Additive-only: `deprecated_at` rather than `DELETE`; a new name rather than a rename
  or retype.
- Enum-like columns (`resolution_mode`, `time_basis`, `kind`) are `TEXT` + `CHECK`, not
  native Postgres enums — cheaper to widen later and no transactional migration issues.
- `MetaData` carries a `naming_convention` from the first migration, so autogenerated
  downgrades can name their constraints.

## 4. Physical layout — long format

Every feature parquet has the identical schema:

```
entity_id       string          (dictionary-encoded)
event_time      date32
knowledge_time  timestamp[us]   nullable
ingest_time     timestamp[us]
feature_name    string          (dictionary-encoded)
value_num       double          nullable
value_str       string          nullable
```

**Why long, not wide:**

1. `knowledge_time` attaches to a *fact*, not a row. Wide format forces every column in
   a row to share a revision cadence, which is false — GDP is revised, population is not.
2. Adding a feature is an append, not a schema migration across every registered file.
3. Combining sources becomes `UNION ALL`, not an N-way join.

**Wide is a derived form only.** Composition pivots at freeze time and writes a wide
parquet as a `materialized` dataset_version. Wide never exists as a registered layout.

**Layout rules:**

- Path: `features/{group}/entity_namespace={ns}/[year={y}/]part-NNNN.parquet`
- Sort by `(feature_name, entity_id, event_time)` before writing — makes row-group
  min/max statistics tight on `feature_name`, so a query for 3 indicators skips the row
  groups holding the other 1,397.
- Partition by year only when volume justifies it. Annual country panels are a few
  hundred rows per year; don't create 60 tiny files.
- Write `feature_group` name and `entity_namespace` into parquet key-value metadata, so
  a bare file stays interpretable if the catalog is lost or rebuilt.

**Boundary:** features are long rows; per-record dense vectors (embeddings) belong in a
fixed-size-list parquet as a separate dataset kind; media belongs in content-addressed
blobs. The latter two are out of the current scope.

## 5. Time semantics

Three timestamps wherever facts live:

| column | meaning |
|---|---|
| `event_time` | when the thing happened / the period it describes |
| `knowledge_time` | when the value became available |
| `ingest_time` | when it landed in our store |

`knowledge_time` is **not** file download time. Stamping 2024 archives with a 2026
download date makes every as-of query before 2026 return nothing.

`feature_group.time_basis` records how the knowledge_time was determined:

| basis | meaning |
|---|---|
| `publisher_timestamp` | source gave a per-row availability time |
| `file_release` | vintage / release date of the file (e.g. `WEOApr2024`) |
| `modeled_lag` | `event_time + declared_lag`, rule in `meta` |
| `ingest_fallback` | download time; an upper bound, not precise |

**`modeled_lag` knowledge_time is derived, not materialized** — the column is null in
parquet and resolved at read as
`COALESCE(knowledge_time, event_time + declared_lag)`. Correcting a lag rule is then a
Postgres metadata update, not a parquet rewrite.

Fidelity is monotonic: `ingest_fallback → modeled_lag → file_release →
publisher_timestamp`, never backwards. Upgrading fidelity produces a **new**
dataset_version with lineage to the old — never an in-place edit, or frozen query
versions would silently resolve to different data.

**Error direction matters.** Placeholder knowledge_times are pessimistic: they withhold
data that was genuinely available, so prior results were conservative rather than
contaminated. Discovering data arrived *later* than assumed is the dangerous direction —
it invalidates prior results.

## 6. Entity namespaces and crosswalks

The catalog holds the **join key**, not entity knowledge. `entity_namespace` registers
vocabularies (`iso3166-1-alpha3`, `worldbank-country`, `imf-country`, `gdelt-actor`,
project-local). No entity rows, no aliases, no succession logic.

**One enforced rule:** feature groups in different namespaces cannot be joined without a
named crosswalk. World Bank, IMF, and ISO three-letter country codes mostly agree and
quietly don't (ROM/ROU, ZAR/COD, ADO/AND), plus aggregates present in one and absent in
another. Without the rule, those joins succeed and drop rows silently.

A **crosswalk** is an ordinary dataset with `kind='crosswalk'`:
`(source_id, target_id, valid_from, valid_to, confidence)`, with source and target
namespaces in `meta`. Compositions name a crosswalk *version* — pinned, hashed,
lineage-tracked, never resolved at runtime. Entity resolution improves over time;
unpinned resolution would silently rewrite historical joins.

Prefer public vocabularies (Wikidata QIDs as general fallback) over minting canonical ids
that then need maintaining.

## 7. Composition

Engine: DuckDB with `httpfs`, reading parquet directly from object storage.

```sql
WITH facts AS (
  SELECT cw.target_id AS entity_id, event_time,
         COALESCE(knowledge_time, event_time + INTERVAL 18 MONTH) AS kt,
         feature_name, value_num
  FROM read_parquet('s3://.../features/wdi/**')
  JOIN crosswalk cw ON cw.source_id = entity_id
  UNION ALL
  SELECT cw.target_id, event_time, knowledge_time, feature_name, value_num
  FROM read_parquet('s3://.../features/weo/**')
  JOIN crosswalk cw ON cw.source_id = entity_id
)
SELECT s.entity_id, s.as_of, f.feature_name, f.value_num
FROM spine s
ASOF JOIN facts f
  ON s.entity_id = f.entity_id AND f.kt <= s.as_of
-- then pivot to wide at freeze
```

Cross-dataset combination is a **UNION**, not a join — identical schemas mean no column
collisions and no schema reconciliation. The only real joins are the crosswalk and the
spine.

**Granularity mismatch resolves for free.** Attaching country-year GDP to a country-week
spine needs no resampling logic: the as-of join carries the most recent known value
forward and updates when the next vintage lands.

**Staleness must be visible.** A value from 2019 and one from last week look identical in
the output. Carry the resolved `knowledge_time` (or a derived `age_days`) alongside each
feature, and support a per-feature `max_age` bound beyond which the value resolves to
null rather than carrying forward indefinitely.

## 8. Composition spec (the artifact)

Pydantic model, JSON Schema exported for editor validation. Fields:

- target entity namespace
- spine definition (entities × timestamps)
- feature selection across groups (the pivot list)
- crosswalk version pins
- as-of policy
- per-feature staleness bounds
- output orientation, freeze mode

**Canonical serialization is defined before anything is hashed:** sorted keys, fixed
separators, defaults materialized explicitly, schema version included. Hash the canonical
form, never the raw file — otherwise reformatting rewrites the lineage graph.

`dataset_version.resolution_mode`:

| mode | meaning |
|---|---|
| `query` | predicate + pinned as-of cutoff + pinned crosswalk versions; resolves identically forever without copying bytes |
| `materialized` | frozen parquet, content-addressed, immutable |

## 9. Invariants

1. **Knowledge-time monotonicity** — a run's output `knowledge_time` ≥ max
   `knowledge_time` of its inputs. Asserted in lineage write-back. Catches most lookahead
   bugs that survive the join logic.
2. **Namespace guard** — cross-namespace joins without a pinned crosswalk are an error,
   not a warning.
3. **Write order** — parquet first, verify, *then* insert the catalog row. A failure
   leaves an orphan file, never a catalog entry pointing at nothing. A `verify` command
   walks the catalog and checks every `storage_prefix` resolves.
4. **Lineage is automatic, never opt-in.** Optional lineage gets skipped, and the catalog
   drifts into fiction within two projects.
5. **Frozen versions are immutable.** Corrections produce new versions; old pins keep
   resolving to old data.

## 10. Testing

Integration tests against a **live Postgres and a live Garage container** (testcontainers
or `pytest-postgresql`), not mocks. Mocking S3 defeats the point of having chosen an
S3-compatible store, and this is the highest-signal thing in the repo.

CI additionally runs `alembic upgrade head → downgrade base → upgrade head` against a
clean database, catching missing downgrades and dependency-order bugs while the schema is
small.

## 11. Forward path

The full platform adds, without unwinding anything here:

- `blob` (sha256-addressed) and `record` — unstructured corpora
- `label` / `comparison` / `label_schema` — append-only, closed primitive set
  (classification, span, bbox, polygon, keypoints, relation, generation, rating/preference),
  with `source_type` / `derived_from` provenance so human verification appends rather than
  mutates
- `model_version` — pointer + framework tag + metrics, no deserialization
- processing repo — step registry + declarative pipeline runner
- labelling repo — format converters and the Label Studio bridge; depends on the catalog,
  never the reverse
- knowledge base — owns aliases, hierarchy, succession; interfaces by *emitting*
  crosswalks, never queried at runtime

Ordering principle throughout: **a real consumer forces each abstraction into existence.**
Plugin seams are designed at the third implementation, not the first.

---

## 12. Decisions worth recording as ADRs

- Long format; wide as derived output only
- Bitemporal storage, and what `modeled_lag` means
- Entities live outside the catalog; interface by materialized crosswalk
- Crosswalk versions are pinned, never resolved at runtime
- No `StorageBackend` abstraction
- Garage over MinIO (MinIO's OSS repo was marked unmaintained in Dec 2025)
- `TEXT` + `CHECK` over native Postgres enums
- Frozen versions immutable; fidelity upgrades create new versions

Dormancy of several months is the normal case for a background project. Re-deriving these
from scratch is what turns a pause into an abandonment.
